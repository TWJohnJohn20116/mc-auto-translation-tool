# MCAutoTranslationTool 全面審計 — 統一規則、編號號段與回報格式

本檔由 Team Lead 撰寫，所有子代理（含孫代理）**必須先完整讀完本檔**再開始工作。
本檔是唯一編號權威，違反號段會造成合併時編號衝突。

---

## 0. 絕對規則（違反即作廢）

| 禁止 | 說明 |
| --- | --- |
| 編譯 / 建置 / 打包 | 不得呼叫 `gradlew`、`gradle`、`javac`、`java`、任何 JDK 工具鏈 |
| 執行專案腳本 | 不得執行 `scripts/*.ps1`、`scripts/*.py`、`setup_defender_exclusions.bat` |
| 跑測試 | 不得跑 `unittest` / `pytest` / Gradle `test` / `check` |
| 本機驗證 | 唯一建置途徑是 GitHub Actions；本審計**不需要**任何建置 |
| 寫入他人檔案 | 只能寫自己那一個報告檔（見 §5），不得改動 `src/` 內任何程式碼 |
| git 寫操作 | 不得 `commit` / `push` / `checkout` / `reset` |
| 審計 `build/`、`.gradle/`、`node_modules`、`dist/`、`__pycache__` | 這些是產物，不是原始碼 |
| 審計 `_re/` | 這是反向工程殘留目錄，與本專案無關，排除 |

允許：`read`、`grep`、`glob`、`pwsh`（僅限檔案列舉／統計／讀取，不執行專案程式碼）。

## 1. 專案概觀（避免重複摸索）

- 單一 Gradle 多專案：`translator-core`（共用核心，以 `srcDir` 掛進每個平台）+ `platforms/{fabric,forge,neoforge}`

  - `PersistentTranslationCache`（279 行）
  - `ProtectedText`（338 行，佔位符保護）
  - `net/HttpJsonClient`（317 行）+ `net/JsonStrings`（397 行，手寫 JSON 解析器）
  - `provider/OpenAiChatTranslationProvider`（1096 行）、`provider/LlamaCppOfflineProvider`（814 行）、`provider/OnlineProviderConfig`（594 行）
  - `offline/OfflineProcessSupport`（507 行）、`offline/SafeArchiveExtractor`（369 行）、`offline/VerifiedDownloader`（255 行）
- UI 巨型類（真正的手寫 UI，無框架）：
  - `platforms/fabric/shared/screens-shared/.../UniversalTranslatorSettingsScreen.java`（1302 行）

## 2. 嚴重度定義（判斷標準，不要憑感覺）

| 級別 | 前綴 | 判定 |
| --- | --- | --- |
| 嚴重 | `BUG-C` | 崩潰／例外未捕捉導致功能全滅、資料遺失或損毀、快取永久污染、啟動失敗、記憶體／執行緒無限增長最終 OOM、機密（API Key）外洩到日誌或網路、跨版本載入失敗 |
| 中 | `BUG-M` | 功能明顯不正確但可繞過、特定版本或特定條件下失效、明顯效能劣化（每次渲染都做重活）、資源洩漏（串流／執行緒／檔案句柄未關）、競態導致偶發錯誤 |
| 小 | `BUG-S` | 文案／在地化錯誤、邊界值Off-by-one、日誌級別或訊息錯誤、樣式與版面、死碼、命名不一致、罕見路徑未處理、可讀性造成的維護風險 |
| 功能缺口 | `FG` | 「應該有但沒有」的能力（相對於 Minecraft 翻譯模組的合理期待、以及既有 provider／平台矩陣的空缺） |
| 最需要功能 | `NF` | 使用者價值排序前 5，做了會顯著改變體驗 |
| 性能屎山 | `PERF` | 結構性設計導致的效能問題（不是單行 micro-opt），要有量化推理（每幀次數 × 資料量） |

**判斷紀律**：不確定是不是 bug 就降級並在「信心」欄標 `低`；寧可標低，不要虛報嚴重。

## 3. 每條發現的固定格式（合併時機械化處理，格式錯就退件）

````markdown
### BUG-C-001 · 一句話標題（≤30 字，動詞開頭）

- **嚴重度**：嚴重 ｜ **信心**：高
- **位置**：`translator-core/src/main/java/org/universaltranslator/core/TranslationCoordinator.java:212-240`
- **受影響範圍**：所有平台 / 僅 Fabric 1.16–1.20 / 僅離線引擎 …
- **現象**：使用者或系統觀察到什麼。
- **觸發條件**：什麼輸入／時序／版本會踩到（要具體，不要「可能」）。
- **根因**：程式碼層面為什麼會這樣（引用關鍵行）。
- **影響**：後果與量級（例：每幀多 1 次 JSON 解析，20 tick/s × 60 幀）。
- **修法**：具體做法 + 必要時給 patch 片段。

```java
// 建議改法（可只給關鍵幾行）
```
````

`FG` / `NF` / `PERF` 用同一骨架，但欄位換成：

- `FG`：`缺口描述` / `現狀` / `為什麼算缺口` / `最小可用實作路徑` / `涉及檔案`
- `NF`：`需求` / `痛點證據`（引用程式碼或文件） / `使用者價值` / `實作範圍估計` / `風險`
- `PERF`：`熱點` / `呼叫頻率×資料量估算` / `根因（結構性）` / `量化影響` / `重構方向` / `預估收益`

**硬性要求**

1. 每一條都必須有 `檔案:行號`，行號要真的對得上（`read` 過再寫）。
2. 不得出現「可能」「也許」「建議檢查」當結論；不確定就標信心低並寫清楚不確定在哪。
3. 同一根因在不同檔案重複出現時，合併成一條並列出所有位置。
4. 不得把 `AGENTS.md` 已記載且已修復的歷史事故當新 bug 重報（可寫成「同類風險殘留」並指出還沒修的地方）。
5. 報告末尾附「已排查但判定無問題」清單（3–8 條），證明有覆蓋而不是憑空生成。

## 5. 寫入規則

- 只寫自己那一個 `.md`（路徑見 §4 表格）。
- 目錄 `reports/audit/` 已存在。
- 檔頭固定：

```markdown
# <agent 名稱> 審計報告
範圍：<你負責的路徑>
配額：<你被分配的數量>
產出：BUG-C x / BUG-M x / BUG-S x（實際）
```

- 依 `BUG-C → BUG-M → BUG-S`（或 FG / NF / PERF）順序排列。
- 檔尾固定「已排查但判定無問題」清單。

## 6. 完成後的訊息
